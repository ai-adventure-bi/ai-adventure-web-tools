Open `web-hq/database/UPGRADE-2026-11-27.sql` from the extracted archive. Copy the entire file into the SQL editor of the Supabase project already used by Web HQ and run it.

## 3. Teacher publication workflow

Students keep editing and saving private drafts as before. **Publish changes → Send for teacher approval** stores an immutable submitted version and places it in **Review websites**. It does not publish that version to the class or other schools. If an older version is already published, that version stays live while the update is waiting.

Assigned teachers and admins open **Review websites**, choose a request, inspect its page, optionally open its submitted source, and check the full uploaded media grid. The grid includes unused files. Images open larger; videos open in a player. There are no individual approval checkboxes for each file. One confirmation and **Approve and publish** approves the submitted version and its whole current upload library. **Request changes** sends a short note to the student's editor and keeps any previous published version unchanged.

Later student draft edits do not get included in an earlier submission. Resubmitting replaces the pending request, so a stale request cannot be approved. Approval is checked again on the server; students cannot approve themselves or bypass it by directly calling Publish. Teachers are limited to their assigned classrooms, including classrooms with several assigned teachers. Admins can review all classrooms. Staff-owned websites can still be published directly by staff.

The student editor updates review status when focused and approximately every 15 seconds while open. The teacher queue has a Refresh requests button. There are no email notifications.

## 4. Media safety and removal

New uploads stay private to their owner and managing staff until the teacher approves a publication. Approval covers the whole library, while unused media remains inaccessible to ordinary visitors. Uploading or removing files changes the library revision. If that happens after a teacher loaded the review, the approval is rejected until the teacher refreshes and checks the library again.

**Remove file** permanently deletes that uploaded image/video from this website's library. It affects every version using the same file reference. Source references remain in place: normal HTML image elements display the browser's missing/broken-image indicator on the next load instead of a silently substituted transparent image. Removed videos cannot play; CSS backgrounds and Three.js textures may fail differently because they are not HTML image elements. The teacher can remove a file while reviewing, then refresh and approve once they have checked the remaining library.

Removal also clears stored thumbnails for every version of that website, so a thumbnail cannot retain the removed picture. A browser page that already loaded a file must refresh; this cannot retract images already copied, downloaded or cached outside Web HQ. Removal is permanent and should be used only when intended.

This grid covers **uploaded library files**. Images embedded directly in code, external image/video URLs, game-generated content, nicknames and leaderboard entries are not files in that library. Teachers must inspect those through the page/code and existing moderation controls. External websites can change after approval. The approval system supports human review; it is not an automated content-safety guarantee. Camera/microphone permissions are unchanged by this update.

Already published websites and their existing uploads remain available after migration; they are not retroactively taken offline. Their next submitted update requires approval. A teacher can take an existing website offline using the existing controls and review it again if needed.

## 5. Select which sites other schools can visit

Open **Settings → Classrooms**, select the school and enable **Allow selected websites to be shared with other schools**, then save. Tick the agreed websites in **Websites shared with other schools** and press **Save sharing choices**.

Existing and new websites start unticked when migration 010 is first applied. They remain available to their own class if published. A site appears to another school only when the school's master switch is enabled, that website is selected, and an approved version is published. Teacher approval does not automatically tick cross-school sharing. Trashing clears the sharing choice. Disabling the school switch hides its sites from other schools but retains the individual selections.

## 6. Online game progress

The built-in `window.SiteStudio.saves.load()` and `.save(progressObject)` API keeps separate private progress for each logged-in player and website. Hosted saves are stored in Supabase Postgres. Website/account IDs come from the host and login session; games receive no database keys. The SDK serialises writes and rejects stale saves from another tab/device.

HeyOtto now receives the save instructions automatically. **Existing games such as Willowbrook need their meaningful progress connected once.** Ask HeyOtto to add private online saves using SiteStudio.saves: load before play, restore inventory/quests/position and other relevant state, autosave changed progress during play, save checkpoints, and show accurate saving/error messages. Review the change and test a new account before classroom use. See `SHARING-AND-GAME-SAVES.md` for the API and a fuller prompt.

Save progress as a small JSON object, at most 128 KiB. Do not use localStorage for account progress or store Three.js scenes, photos, audio or credentials. URL/title changes, publishing and trash/restore keep the save. Permanent website deletion removes its game saves. Closing the page or losing the network before a save is confirmed can lose the latest unsaved changes. This does not add offline saving or automatic compatibility with every existing game state model.

## 7. JavaScript error isolation

An unrelated extension error or rejected promise is now a nonfatal diagnostic rather than a reason to remove a running game. Compilation, caught startup failures and React render failures are handled separately. Diagnostics sits below the game, with Restart preview and a copyable report that omits messages, code, stacks, URLs and account data. Frame message source/origin/channel checks are enforced. Essential runtime dependencies remain self-hosted.

Direct localStorage/IndexedDB and camera/microphone access remain unavailable inside the existing isolated sandbox; the private save API does not weaken that boundary. Infinite loops, browser/GPU crashes and every possible extension action cannot be made harmless by error handlers.
