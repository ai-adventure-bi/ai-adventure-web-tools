# Leaderboards and website addresses

Restart `Start Studio.cmd` and refresh after updating. Local database migrations run automatically. Existing projects receive address-history records without changing their URLs.

## Enable an online leaderboard

Ask HeyOtto to add a leaderboard or high-score table. The coding instructions always explain Studio’s built-in leaderboard API, so students do not need to provide an API prompt or enable a setting first. When compatible code is saved, Studio automatically connects the leaderboard. Save and publish as usual; the publish confirmation explains the leaderboard sharing. An existing explicit pause is preserved. Anyone with the public leaderboard link can see the entered names and scores. Game code submits the calculated final score with the nickname, without a separate leaderboard login. It does not make the classroom or game itself public; normal Studio website viewing still requires a Studio login.

Player names are free text, limited to 30 characters on one line. Encourage nicknames. There are no player accounts, unique-name checks or ownership claims over a nickname. Scores must be nonnegative whole numbers no larger than one billion. Up to 50 entries are returned. Games can request descending order (high scores) or ascending order (fastest times). Up to 200 entries are retained, covering the highest 100 and lowest 100 scores. Submissions are limited to 10 per minute per game/network address and 1,000 per day per game. People sharing a school network may share that limit. Scores are unverified, player-submitted values and can be fabricated.

The general leaderboard controls panel has been removed from the student editor. Existing server management endpoints still enforce owner/assigned-staff permissions for pausing or clearing a board. Automatic setup needs no student-facing configuration. Turning it off keeps entries but blocks public reading and writing. Taking the game offline also blocks leaderboard access. The standalone `/leaderboard/PROJECT-ID` page shows scores to guests; there is no manual score-entry form. Scores are submitted by the game. The stable project ID keeps the board attached when the website address changes.

## What to ask HeyOtto

Students can simply ask “Add a leaderboard to my game”. The exact API instructions below are supplied to HeyOtto automatically:

> Add a leaderboard to this game using Site Studio's existing API. Ask the player for a nickname without requiring login. When a game ends, call `await window.SiteStudio.leaderboard.submit(playerName, finalScore)`. Load the highest scores using `await window.SiteStudio.leaderboard.list()`, which returns an array of `{id, name, score, created}` objects. Render names as text. Show loading and error messages and prevent duplicate submissions while saving. Do not add Supabase keys, fetch calls or a separate backend. Keep the existing game and add touch-friendly controls.

These methods work inside Studio's game preview and published-game sandbox. They pass through a narrow parent-page bridge; generated code does not receive credentials or access to other games' data. Save and publish a game with the built-in leaderboard code before testing online score submissions. No manual setup step is needed unless an owner has explicitly paused the leaderboard. Ordinary thumbnails do not get leaderboard access. Existing games must be adapted to call these methods; automatic setup cannot replace arbitrary storage code already generated by HeyOtto. Ask the helper to adapt existing custom leaderboard code to the built-in API.

Local scores are saved in `.local/classroom.sqlite`. Under the Vercel adapter they are saved in Supabase Postgres, in the private `studio.scores` table. This update does not migrate local scores into a hosted database.

## Change a website's address

Use the Website address box below Save draft/Publish, edit the final part, and choose **Save address**. The box shows **Address saved** when it matches the saved address. This changes the final part of `/c/class-address/website-address`. Use lowercase letters, numbers and single dashes, up to 48 characters. The page title and its URL are independent, so a draft title edit does not unexpectedly change a published link.

Old addresses remain reserved to the same website. Studio resolves all historical addresses directly to the current one, updates anchor destinations when another page renders, and resolves navigation again when links are followed. Visiting an old bookmark updates the address bar to the newest address. New class-link insertions use the current address. Students cannot claim another site's previous address.

This updates live link destinations, not the literal text inside other students' source files or exported copies of those files. A displayed handwritten link label does not change automatically. A page already open during a rename may still display its previous address until refreshed, but following it resolves the current destination. Private/unpublished sites retain their existing access restrictions.

## Hosted upgrade

Existing Supabase deployments must run `database/004-leaderboards-addresses.sql` after the earlier numbered upgrades, before deploying this version. New installations use the complete `database/supabase-studio.sql`. Live Supabase/Vercel operation has not been tested in this update.
